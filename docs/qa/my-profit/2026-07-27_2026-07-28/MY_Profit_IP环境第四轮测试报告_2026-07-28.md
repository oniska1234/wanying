## 六、P0 缺陷

### BUG4-P0-001：Auth.js 仍使用 HTTP 规范地址，Cookie 缺少 Secure

HTTPS 登录响应：

```text
Location: http://47.106.167.145
authjs.session-token=...; Path=/; HttpOnly; SameSite=Lax
authjs.callback-url=...; Path=/; HttpOnly; SameSite=Lax
```

缺少：

```text
Secure
```

风险：

- 用户从 HTTP 地址进入时，Session Cookie 可能在 301 跳转前被发送；
- 登录回调发生 HTTPS → HTTP 降级；
- 会话存在被网络窃取的风险。

修复建议：

1. 将 `NEXTAUTH_URL`/Auth.js 规范 URL 改为当前 HTTPS IP；
2. Nginx 设置 `X-Forwarded-Proto $scheme`；
3. 检查 `X-Forwarded-Host`；
4. 强制 Session、CSRF、Callback Cookie 使用 Secure；
5. 修改后使现有 Session 失效。

即使当前证书是自签名，HTTPS 页面设置的认证 Cookie 仍应使用 Secure。

## 七、P1 缺陷

### BUG4-P1-001：安全响应头发生回归

第四轮 GET 和 HEAD 响应均未发现：

- Strict-Transport-Security；
- X-Content-Type-Options；
- X-Frame-Options；
- Referrer-Policy；
- Content-Security-Policy；
- Permissions-Policy。

第二轮中前四项曾经存在，说明部署或 Nginx 配置发生回归。

建议将安全头配置放在统一 HTTPS `server` 块，并加入部署后自动检查。

### BUG4-P1-002：未知类目静默使用通用费率

请求类目：

```text
Unknown > Category
```

实际：

```text
HTTP 200
商品保存成功
```

原因是 `*` 通用佣金规则可以匹配任意未知类目。

风险：

- 拼写错误或未来自动解析类目失败时，会得到看似完整的利润；
- 用户无法知道系统没有匹配精确类目；
- “精准利润”承诺不成立。

建议：

- 服务端校验类目必须属于已发布类目集合；
- 明确区分用户主动选择“通用费率”和未知类目；
- 使用通用费率时显示醒目提示并要求确认；
- 保存快照记录 `matchLevel: exact/parent/default/custom`。

### BUG4-P1-003：平台支持费生效日期错误

API 当前：

```text
fixedAmount: 0.54
effectiveFrom: 2024-09-04T16:00:00Z
```

RM0.54 平台支持费的官方生效时间为 2026-02-15 00:00 Malaysia，对应：

```text
2026-02-14T16:00:00Z
```

当前金额正确，但历史回算会错误地把支持费应用到更早订单。

### BUG4-P1-004：费率类目仍未完全覆盖

规则由 28 条增加到 48 条，类目由 5 个增加到 10 个。当前新增：

- Phones & Electronics；
- Phone Accessories；
- Computers & Office；
- Automotive & Motorcycle；
- Household Appliances。

这是有效改进，但 Fashion、Home & Living、Beauty 等仍为一级类目。正式宣传“精准匹配”前，应确认这些一级类目内部是否存在费率差异。

## 八、P2 问题

### BUG4-P2-001：特定边界下目标售价返回空

在以下场景：

- 卖家折扣 RM10；
- 买家运费 RM5；
- 商品及履约成本为 0；
- 最低合法商品价为 RM10.01；

最低合法价已经达到 20% 目标利润，但结果中的 `suggestedPrice` 返回 `null`。

目标售价求解器应和保本求解器一致：

1. 先计算合法下界；
2. 若下界已经满足目标，直接返回下界；
3. 否则再执行二分求解。
