- 测试日期：2026-07-28
- 测试环境：Production / IP
- 测试地址：`https://47.106.167.145/tools/my-profit`
- 测试方式：HTTPS IP 接口回归、生产构建静态核验
- 测试结论：**不通过**

## 一、测试说明

根据要求，本轮在域名备案期间使用 IP 地址继续测试。

由于 IP 地址仍使用自签名证书，标准浏览器会返回 `ERR_CERT_AUTHORITY_INVALID`。本轮没有绕过浏览器安全拦截，采用以下方式继续：

- 使用隔离 QA 账号调用生产 API；
- 使用 `curl -k` 忽略证书信任，仅用于测试；
- 检查实际生产 JavaScript 构建中的校验、公式和保存弹窗实现；
- 不输入真实用户资料、真实商品成本或真实支付数据。

因此接口、权限、额度和代码逻辑可以得到部分结论；真实 UI、Safari/Chrome 兼容性和移动端交互仍需在可信证书就绪后补测。

## 五、P0 缺陷

### BUG3-P0-001：佣金规则仍不能称为“精准匹配”

费率 API 当前返回 28 条规则，但商品类目只有：

- 通用；
- Electronics；
- Fashion；
- Home & Living；
- Beauty & Personal Care。

例如 API 将所有 `Electronics + Marketplace + BXP` 商品统一使用 5.40%。官方费率实际按子类目变化，电子类中存在 5.40%、7.02%、8.10% 等不同费率。

影响：

- 部分电子商品会被低估佣金；
- 保本价、最高采购价及净利润随之失真；
- 产品“专属精细化利润核算”的核心卖点无法成立。

修复建议：

1. 类目至少细化到官方费率能够唯一确定的层级；
2. 使用 TikTok 类目 ID，不只使用英文名称；
3. 无法精确匹配时禁止输出“精准利润”；
4. 提供手动费率覆盖，并标记为自定义；
5. 为每个子类目建立金样。

### BUG3-P0-002：费率接口失败时静默使用旧错误规则

生产前端构建仍包含旧演示规则：

```text
交易费：2%
平台支持费：RM1 或 RM1.5
版本：v1
```

前端逻辑在费率 API 返回失败或无数据时使用该规则集合，而且没有明确的“费率数据不可用”阻断提示。

影响：

- 网络波动或 API 故障时，用户会得到看似正常、实际错误的利润；
- 页面仍会展示规则明细，用户难以意识到已进入降级模式。

修复建议：

- 删除旧演示费率；
- 规则加载完成前禁用计算按钮；
- API 失败时阻止精准计算；
- 如使用缓存，必须保存规则版本和更新时间，并醒目标记“缓存规则”；
- 不允许静默切换到不同费率。

### BUG3-P0-003：平台折扣被错误扣减卖家收入

生产构建当前总交易额公式：

```text
商品原价
- 卖家折扣
- 平台折扣
+ 买家运费
+ 其他收入
```

但当前佣金和交易费公式均不将平台资助折扣作为卖家折扣。平台资助折扣通常不应再次减少卖家收入。当前实现会在填写“平台折扣”时压低总收入和净利润。

风险示例：

```text
商品原价：RM100
卖家折扣：RM0
平台折扣：RM20
```

当前系统按 RM80 作为卖家商品收入，但平台折扣若由平台承担，卖家收入不应少 RM20。

修复建议：

- 将字段拆为“卖家承担折扣”和“平台资助折扣”；
- 只有卖家承担部分减少卖家收入；
- 按官方计费口径分别定义佣金、交易费和收入基数；
- 使用真实结算单确认平台补贴入账方式。

### BUG3-P0-004：会话 Cookie 未设置 Secure

通过 HTTPS 登录后，响应中的 Cookie 为：

```text
authjs.session-token=...; Path=/; HttpOnly; SameSite=Lax
authjs.csrf-token=...; Path=/; HttpOnly; SameSite=Lax
```

缺少：

```text
Secure
```

同时登录回调：

```text
Location: http://47.106.167.145
```

影响：

- 用户先访问 HTTP 时，Session Cookie 可能在重定向前以明文发送；
- 会话存在被窃取风险；
- Auth.js 仍认为站点的规范地址是 HTTP。

修复建议：

- 将 Auth.js 的规范 URL 配置为 HTTPS；
- Nginx 正确传递 `X-Forwarded-Proto: https`；
- Session、CSRF 和 Callback Cookie 均设置 Secure；
- Callback URL 不得降级为 HTTP；
- 修改后使现有 Session 失效。

## 六、P1 缺陷

### BUG3-P1-001：免费额度可通过并发请求绕过

顺序测试：

```text
第 10 条：200
第 11 条：403
最终数量：10
```

并发测试：

```text
同时发送 11 个保存请求
11 个请求全部返回 200
最终数量：11
```

原因推断：

额度判断和商品创建不是一个原子操作。多个请求同时读取到旧数量后均获得创建权限。

修复建议：

- 在数据库事务中执行计数和创建；
- 对用户记录加行锁，或使用原子额度计数；
- 增加幂等键；
- 修复后使用 20、50 并发重新压测。

### BUG3-P1-002：服务端接受客户端提供的利润快照

产品 API 接收并持久化：

- `netProfit`；
- `netMargin`；
- 平台费用；
- 保本价；
- 最高采购价；
- 费率版本；
- 费用明细。

接口没有根据 `form` 和当前费率重新计算核对。测试中提交自定义费用及利润数值可以成功写入。

影响：

- 浏览器控制台或自制请求可以生成伪造利润记录；
- 导出、分享或后续统计可能使用不可信数据；
- 前后端无法保证同一输入得到同一结果。

修复建议：

- 服务端只接受原始输入；
- 由服务端重新匹配费率并计算结果；
- 保存计算输入、服务端结果、规则版本及公式版本；
- 客户端结果仅用于即时展示，不作为持久化权威值。

### BUG3-P1-003：缺少 SKU 的商品可以创建

请求：

```json
{"name":"QA-R3-缺SKU"}
```

实际：

```text
HTTP 200
商品创建成功
```

PRD 的保存对象应为计算快照，缺少 SKU、输入和结果时不应成功。

预期：

```text
HTTP 400
明确指出 sku/form/result 缺失
```

### BUG3-P1-004：部分非法快照返回 500

当提交完整但业务非法的负数售价快照时，接口返回空响应及 HTTP 500。

预期：

- 在进入数据库前完成 Schema 与业务校验；
- 返回 HTTP 400/422；
- 响应包含稳定错误码和字段错误；
- 不在服务端日志中暴露堆栈或敏感内容。

### BUG3-P1-005：选品标签和备注仍使用 prompt()

主保存流程已修复，但选品列表中的：

- 编辑标签；
- 编辑备注；

仍调用 `window.prompt()`。这会影响自动化、字段校验和移动端体验。

建议统一改为应用内弹窗或行内编辑。
