## 4. 第二轮新增/遗留缺陷

### P1-201：同名文件在 ZIP 中仍会覆盖

任务包含：

```text
QA-IMG-CN-DENSE.png
QA-IMG-PRODUCT-VERTICAL.jpg
QA-IMG-PRODUCT-VERTICAL.jpg
```

数据库和 OSS 为 3 个独立成功结果，但 ZIP 中只有：

```text
QA-IMG-CN-DENSE_translated.jpg
QA-IMG-PRODUCT-VERTICAL_translated.jpg
```

原因是 ZIP 文件名仍由原始 `fileName` 生成，同名时 JSZip 使用后一个覆盖前一个。

建议使用：

```text
原文件名_translated_1.jpg
原文件名_translated_2.jpg
```

或加入 item ID 短后缀，并在添加 ZIP 前做名称去重。

### P1-202：历史列表异常分页参数触发 500

请求：

```text
/api/image-translate/tasks?page=abc&page_size=abc
```

结果：

```text
HTTP 500
Prisma skip: NaN
```

此外，`page_size=0` 和 `page_size=-1` 会原样进入 Prisma。应将参数解析结果限制为：

```text
page >= 1
1 <= page_size <= 50
```

非法值应回退默认值或返回结构化 400。

### P1-203：高密度中文图处理耗时过长

1.8MB、1024×1536 的高密度样本单张约耗时 379 秒，在此期间任务仅显示：

```text
processing, done_count=0
```

风险：

- 用户误以为任务卡死并重复提交；
- 多用户同时上传时 CPU 和外部翻译 API 调用会堆积；
- 每张图逐 OCR 区域串行调用 Qwen，文本越多耗时越长。

建议：

- 同一图片的 OCR 文本一次性批量提交给 Qwen；
- 前端展示“正在识别/翻译第 N 张”的细分进度；
- 设置单图处理超时和任务最长时限；
- 加用户级并发限制和全局工作队列；
- 对高密度详情图提示预计耗时。

### P1-204：Python 任务状态仍不持久化

Python 服务仍使用：

```python
tasks: dict[str, dict] = {}
```

服务重启后，正在处理的任务无法恢复。当前 Next.js 层会在 Python 返回 404 时把任务标记为失败，避免永久 processing，但用户仍需重新上传。

建议后续引入 Redis/数据库队列或 Celery/RQ，并使处理步骤幂等、可重试。

### P1-205：译文和版式仍需人工复核

目前结果已可读，但仍有：

- 生硬直译；
- 地名表达不自然；
- 长译文区域拥挤；
- 局部对比度不足。

建议用 30–50 张真实 1688 商品主图/详情图建立人工金标集，按“中文残留、语义、马来本地化、对比度、越界、遮挡、主体破坏”七个维度评分。达到约定阈值后再承诺“可直接上架”。
